# KubeWise：面向 Kubernetes 集群的智能自动运维 Agent 系统


## 一、目标问题与意义价值

KubeWise 是一套面向 Kubernetes 集群的智能自动运维 Agent 系统，应用于云原生集群管理、智能运维、安全审计和应用部署等场景。作品关注 Kubernetes 使用过程中存在的高门槛问题：命令体系复杂、资源对象众多、故障排查链路长、安全检查维度分散、Helm 应用部署步骤繁琐。传统运维方式通常要求用户熟悉 `kubectl`、`helm`、Kubernetes 资源模型以及多个排障命令组合，对初学者、开发人员和一线运维人员都存在较高使用成本。

Kubernetes 集群中的常见任务往往不是单条命令能够完成的。例如，排查一个 Pod 无法启动的问题，用户可能需要依次查看 Pod 状态、容器日志、事件、节点状态、Service Endpoints 和资源配置；安全审计时则需要同时检查 RBAC 权限、Pod 安全配置、NetworkPolicy 覆盖情况和镜像配置风险。这些任务对经验依赖强，人工操作容易遗漏信息。

KubeWise 的目标是将复杂的 Kubernetes 运维任务转化为自然语言交互。用户只需要表达目标，例如：

```text
列出所有 namespace
检查 default 命名空间下有哪些异常 Pod
扫描集群中的安全风险
把 nginx deployment 扩容到 3 个副本
部署一个 nginx ingress controller
```

系统即可自动完成意图识别、任务分发、工具调用、结果整理和必要的用户确认。

作品实现的基本功能包括：

- 集群资源查询：支持 namespace、Pod、PV/PVC、ConfigMap、自定义资源、资源详情等查询。
- 运维操作：支持扩缩容、滚动重启、删除资源、Server-Side Apply、标签和注解修改、节点维护等。
- 故障排查：支持日志、事件、节点状态、Service Endpoints 等信息收集和综合分析。
- 安全审计：支持 RBAC、Pod 安全、NetworkPolicy、镜像安全四个维度检查。
- 智能部署：基于 Helm Chart 实现应用解析、Chart 选择、values 生成、部署计划确认、预检查、部署和验证。
- 会话管理：支持历史会话保存和加载，便于多轮使用。

作品的意义价值主要体现在以下方面：

- 降低 Kubernetes 学习和使用门槛，使用户通过自然语言完成常见运维任务。
- 提升运维效率，将多条命令、多阶段分析流程封装为智能任务。
- 增强安全审计能力，将分散的安全检查整合为统一入口。
- 规范写操作流程，通过计划和确认机制增强可控性。
- 提供平台集成能力，通过 HTTP API 和 SSE 流式事件接入外部系统。
- 展示大语言模型 Agent 在云原生运维场景中的工程化落地方式。

## 二、设计思路与方案

### 2.1 总体设计思路

KubeWise 的总体设计思路是“自然语言入口 + 多 Agent 分工 + 工具注册中心 + Kubernetes API 执行 + 流式可视化反馈”。系统不让大模型直接执行任意命令，也不让大模型直接访问集群，而是将 Kubernetes 和 Helm 能力封装为受控工具。大模型负责理解用户意图、规划步骤和选择工具，系统负责执行已注册工具并返回结构化结果。

这一设计兼顾智能性和可控性：

- 智能性来自大模型的自然语言理解、意图分类和任务规划。
- 可控性来自工具白名单、读写工具分离和用户确认机制。
- 可观察性来自统一的流式事件系统和 TUI 进度展示。
- 可扩展性来自模块化 Agent 和工具注册中心。

### 2.3 技术路线

系统运行流程如下：

```text
用户输入自然语言
  → Router Agent 进行意图分类与实体抽取
  → 路由到对应子 Agent
  → 子 Agent 根据任务选择工具
  → Tool Registry 查找工具实例
  → 工具调用 Kubernetes API 或 Helm SDK
  → 工具结果返回给大模型
  → 大模型生成最终回答
  → TUI/API/CLI 展示结果
```

### 2.4 Agent 设计方案

Router Agent 负责入口分发。它调用大模型，将用户输入分类为 query、operation、troubleshooting、security、deploy 五类任务，并提取 namespace、resource_name、resource_type、app_name、operation 等实体。

Query Agent 负责只读查询。它加载查询工具，适合资源列表、详情、配置、关联关系和状态查询。

Operation Agent 负责写操作。它采用“规划-确认-执行”的流程，先生成结构化操作计划，再由用户确认后执行。

Troubleshooting Agent 负责故障排查。它自动收集日志、事件、节点和服务端点信息，并输出原因分析。

Security Agent 负责安全审计。它覆盖 RBAC、Pod 安全、网络策略和镜像安全。

Deploy Agent 负责完整应用部署。它使用 Helm 完成 Chart 选择、values 生成、部署计划、预检查、安装、验证和恢复。

### 2.5 工具设计方案

系统通过 `Tool Registry` 管理工具。每个工具包含：

- 工具名称。
- 工具描述。
- 参数 Schema。
- 执行函数。

工具分为查询工具、操作工具、排障工具和安全工具。大模型只能调用已注册工具，不能直接执行任意系统命令。

### 2.6 交互设计方案

系统提供三种交互方式：

- CLI：适合快速单次任务。
- TUI：适合多轮对话和长任务可视化。
- HTTP API：适合平台集成。

TUI 使用 Bubble Tea 实现，能够显示类似 Claude Code 的转圈思考效果、阶段进度卡片、工具调用结果和用户确认弹窗。API 使用 SSE 输出流式事件，便于前端实时展示执行过程。

### 3.3 入口命令实现

系统入口位于 `cmd/main.go`，支持：

```bash
kubewise chat "列出所有 namespace"
kubewise tui
kubewise serve
```

默认配置文件为：

```text
~/.kubewise.yaml
```

配置示例：

```yaml
llm:
  model: "glm-5.1"
  api_key: "your-api-key"
  api_base: "https://open.bigmodel.cn/api/paas/v4/"

agent:
  max_steps: 20

log:
  level: "info"
  file: "stderr"
```

### 3.4 查询功能实现

查询工具包括：

- `list_namespaces`
- `list_pods_in_namespace`
- `get_pod_detail`
- `get_resource_detail`
- `get_pod_resource_usage`
- `list_persistent_volumes`
- `list_persistent_volume_claims`
- `find_pods_using_pvc`
- `get_configmap_content`
- `list_resources_by_gvr`

例如 `list_namespaces` 工具底层调用：

```go
c.clientset.CoreV1().Namespaces().List(ctx, metav1.ListOptions{})
```

该调用等价于：

```bash
kubectl get namespaces
```

但系统直接调用 Kubernetes API，获得结构化对象，便于进一步分析和展示。

### 3.5 操作功能实现

Operation Agent 支持：

- 扩缩容。
- 滚动重启。
- 删除资源。
- Server-Side Apply。
- 修改标签和注解。
- 节点 cordon / drain。

写操作流程为：

```text
生成操作计划
  → 用户查看计划
  → 用户确认或修正
  → 执行对应写工具
  → 返回执行结果
```

### 3.6 故障排查功能实现

Troubleshooting Agent 可调用：

- `get_pod_logs`
- `get_resource_events`
- `get_node_status`
- `get_service_endpoints`

系统可将日志、事件、节点状态等信息汇总给大模型分析，输出原因和建议。

### 3.7 安全审计功能实现

Security Agent 支持四类审计：

| 审计类型     | 检查内容                                  |
| ------------ | ----------------------------------------- |
| RBAC 审计    | 高权限绑定、危险权限组合                  |
| Pod 安全审计 | privileged、hostPath、root 用户、权限提升 |
| 网络策略审计 | NetworkPolicy 覆盖和命名空间隔离          |
| 镜像安全审计 | latest 标签、镜像来源、拉取策略           |

### 3.8 部署功能实现

Deploy Agent 实现应用部署流水线：

```text
解析应用名称
  → 查找 Helm Chart
  → 获取默认 values
  → LLM 生成自定义 values
  → 生成部署计划
  → 用户确认
  → Helm 预检查
  → 安装或升级
  → 验证结果
  → 失败诊断恢复
```

该流程使系统不仅能查询集群，还能完成应用交付。

### 3.9 API 实现

HTTP API 提供：

| 方法   | 路径                         | 功能         |
| ------ | ---------------------------- | ------------ |

| GET    | `/api/v1/chat/stream`      | SSE 流式问答 |
| POST   | `/api/v1/chat/interaction` | 用户确认     |
| GET    | `/api/v1/sessions`         | 会话列表     |
| POST   | `/api/v1/sessions`         | 创建会话     |
| GET    | `/api/v1/sessions/:id`     | 会话详情     |
| DELETE | `/api/v1/sessions/:id`     | 删除会话     |

## 五、创新与特色

### 5.1 多 Agent 云原生运维架构

作品将 Kubernetes 运维任务拆分为 Router、Query、Operation、Troubleshooting、Security、Deploy 等多个 Agent。不同 Agent 对应不同工具集合和执行流程，使系统具备清晰的任务边界和良好的扩展能力。

### 5.2 自然语言到 Kubernetes API 的完整链路

系统打通了自然语言输入、意图分类、工具选择、Kubernetes API 调用、结果解释和会话保存的完整链路。用户表达目标后，系统能够自动完成从语义理解到真实集群访问的全过程。

### 5.3 工具白名单与读写分离机制

大模型只能调用系统注册工具，不能直接执行任意命令。查询、排障、安全和操作工具可按类别加载，提升系统可控性。

### 5.4 可审查的操作确认机制

对于扩容、重启、删除、apply 等写操作，系统先生成操作计划，再等待用户确认后执行。该机制将智能规划与人工审查结合，适合真实运维场景。

### 5.5 Helm 智能部署闭环

Deploy Agent 不只是调用 `helm install`，而是包含应用解析、Chart 选择、values 生成、部署确认、预检查、部署验证和失败诊断恢复，形成完整的智能应用交付闭环。

### 5.6 TUI 与 API 双形态展示

TUI 提供类似 Claude Code 的终端智能体交互体验，能够展示思考动画、阶段进度和工具调用状态。HTTP API 和 SSE 则使系统具备平台集成能力，可接入 Web 控制台、DevOps 平台或安全管理平台。

KubeWise 通过 Router Agent 将任务识别为查询任务，再由 Query Agent 调用 `list_resources_by_gvr` 工具读取 `kubewise-exp` 命名空间下的 Pod 列表。查询结果显示：`kw-nginx` 处于 `Running/Ready` 状态，`kw-broken` 处于镜像拉取失败相关状态。该结果与 `kubectl get deploy,pod -n kubewise-exp -o wide` 的真实集群输出一致。

### A.3 写操作实验：自然语言扩容 Deployment

扩容前状态：

| 资源 | spec.replicas | readyReplicas | Pod 数量 | Pod 状态 |
| --- | ---: | ---: | ---: | --- |
| `kw-nginx` | 1 | 1 | 1 | `Running` |

KubeWise 调用命令：

```powershell
"y" | .\kubewise.exe chat "把 kubewise-exp 命名空间下的 kw-nginx deployment 扩容到 2 个副本" --config=./examples/config.yaml
```

执行过程体现了 KubeWise 的可控写操作机制：Operation Agent 先生成结构化计划，展示资源、目标副本数和操作说明；用户输入 `y` 后，系统才调用 `scale_resource` 写工具。该工具底层通过 Kubernetes API 更新 Deployment 的 scale 子资源，等价于执行 `kubectl scale deployment/kw-nginx --replicas=2 -n kubewise-exp`，但入口是自然语言。

扩容后验证：

| 资源 | spec.replicas | readyReplicas | Pod 数量 | Pod 状态 |
| --- | ---: | ---: | ---: | --- |
| `kw-nginx` | 2 | 2 | 2 | 两个 Pod 均为 `Running` |

`kubectl rollout status deployment/kw-nginx -n kubewise-exp --timeout=120s` 返回 `deployment "kw-nginx" successfully rolled out`。这说明 KubeWise 不只是生成了建议文本，而是实际改变了集群状态，并且变更结果可以被 Kubernetes 原生命令验证。

### A.4 故障实验：制造 ImagePullBackOff 并诊断根因

故障资源 `kw-broken` 使用了不存在的镜像标签：

| 修复前项目 | 状态 |
| --- | --- |
| Deployment 镜像 | `nginx:not-exist-kubewise` |
| readyReplicas | `0` |
| Pod 状态 | `ImagePullBackOff` |
| 关键事件 | `Back-off pulling image "nginx:not-exist-kubewise"` |

KubeWise 诊断命令：

```powershell
.\kubewise.exe chat "诊断 kubewise-exp 命名空间下 kw-broken deployment 为什么失败" --config=./examples/config.yaml
```

KubeWise 的 Troubleshooting Agent 调用了资源详情和事件查询工具，输出结论为：`kw-broken` 无法形成可用副本，根因是 Deployment 使用了不可拉取的镜像 `nginx:not-exist-kubewise`，kubelet 报告 `ErrImagePull/ImagePullBackOff`。该结论与 Kubernetes 事件中的 `Back-off pulling image` 和 `Error: ImagePullBackOff` 一致。

### A.5 修复实验：通过 KubeWise Apply 修复镜像

KubeWise 修复命令：

```powershell
"y" | .\kubewise.exe chat "修复 kubewise-exp 命名空间下 kw-broken deployment 的镜像问题" --config=./examples/config.yaml
```

系统生成的修复计划为：将 `kw-broken` Deployment 的容器镜像从不存在的标签更新为 `nginx:1.25`，并通过 `apply_resource` 工具执行 Server-Side Apply。用户确认后，KubeWise 提交新的 Deployment YAML，由 Kubernetes 控制器触发滚动更新。

修复前后对比：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 镜像 | `nginx:not-exist-kubewise` | `nginx:1.25` |
| readyReplicas | `0` | `1` |
| Pod 状态 | `ImagePullBackOff` | `Running` |
| rollout 状态 | 无法完成 | `successfully rolled out` |

最终状态中，`kw-broken-865b78c87d-pm7vx` 为 `1/1 Running`，事件记录显示新 Pod 成功调度、镜像可访问、容器创建并启动，同时旧的异常 ReplicaSet 被缩容。这证明 KubeWise 的故障处理闭环包含“发现异常、定位根因、生成修复计划、用户确认、执行修复、验证结果”六个步骤。

### A.6 实验结论

本次真实集群实验验证了 KubeWise 的三个核心能力。第一，查询能力能够把自然语言转换为受控工具调用，并读取 Kubernetes API 中的实时资源状态。第二，写操作能力采用“计划-确认-执行”的流程，能够安全地完成 Deployment 扩容。第三，故障排查能力能够结合资源状态和事件信息定位 ImagePullBackOff 的根因，并通过 Apply 操作完成修复。与传统手工方式相比，用户不需要依次记忆和组合 `kubectl get`、`kubectl describe`、`kubectl get events`、`kubectl scale`、`kubectl apply` 等命令，能够用同一个自然语言入口完成完整运维闭环。
